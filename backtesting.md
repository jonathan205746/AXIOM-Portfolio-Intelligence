# AXIOM Portfolio Intelligence — Backtesting Methodology

## Purpose

This document defines a reproducible and leakage-aware evaluation plan for the portfolio optimizer used by **AXIOM Portfolio Intelligence**.

It intentionally does **not** publish unverified performance numbers. Results such as CAGR, Sharpe ratio, drawdown, or benchmark outperformance must only be added after they are generated by committed code, stored as versioned artifacts, and independently reproducible.

> Historical results are not forecasts. AXIOM is an educational and research system, not an investment-advice or trade-execution service.

## Evaluation questions

The backtest should answer:

1. Does the optimizer outperform an equal-weight portfolio after costs?
2. Does it improve risk-adjusted performance relative to an appropriate market benchmark?
3. Does the FinBERT sentiment overlay add measurable value over quantitative optimization alone?
4. Are allocations stable, diversified, and practical to rebalance?
5. Does performance remain positive across different market regimes and parameter choices?

## Required strategies

Evaluate at least these strategies on identical dates and assets:

| Strategy | Description |
| --- | --- |
| Buy and hold | Initial allocation held without scheduled rebalancing |
| Equal weight | Assets receive equal weights at every rebalance |
| Quantitative only | MPT/risk optimizer without sentiment influence |
| Sentiment only | Bounded FinBERT signal without MPT allocation |
| AXIOM combined | Adaptive quantitative and sentiment pipeline |
| Market benchmark | Suitable index for the selected asset universe |

RAG/LLM text should not directly change historical portfolio weights unless its decision rule is deterministic, versioned, and reproducible. The LLM is primarily an explanation layer in the current product.

## Point-in-time correctness

A valid financial backtest must only use information available at the simulated decision time.

Required controls:

- use adjusted price data available before each rebalance
- use historical index constituents rather than today’s constituents when possible
- respect article publication timestamps
- do not fetch current news to simulate past sentiment
- fit return, covariance, and calibration parameters only on the training/lookback window
- execute simulated trades after the signal becomes available
- record data revisions and provider limitations

If point-in-time news is unavailable, run and label the test as **price-only**. Do not invent historical sentiment values.

## Suggested walk-forward design

| Setting | Recommended starting value |
| --- | --- |
| Price lookback | 252 trading days |
| Rebalance frequency | Monthly |
| Minimum history | 126–252 observations per asset |
| Risk-free rate | Explicit annual assumption stored with each run |
| Maximum asset weight | 20–30%, tested through sensitivity analysis |
| Transaction costs | Explicit basis-point cost per traded notional |
| Slippage | Explicit and separate from commission assumptions |
| Benchmark | Equal weight plus market index matched to the universe |

At each rebalance date:

1. construct the eligible universe using information available at that date
2. select the historical lookback window
3. estimate expected returns and covariance
4. calculate quantitative candidate weights
5. compute point-in-time sentiment only when valid news data exists
6. select the adaptive blend and constraints without using future returns
7. apply turnover and concentration rules
8. deduct costs from executed weight changes
9. hold the portfolio until the next rebalance
10. store inputs, outputs, model versions, and performance

## Core calculations

For prices `P` and daily returns `r`:

```text
r[t] = P[t] / P[t-1] - 1
```

For portfolio weights `w`, expected returns `mu`, and covariance matrix `Sigma`:

```text
Expected return = w.T @ mu
Variance        = w.T @ Sigma @ w
Volatility      = sqrt(variance)
Sharpe ratio    = (annual return - risk-free rate) / annual volatility
```

Turnover at rebalance `t`:

```text
turnover[t] = sum(abs(target_weight - pre_trade_weight))
```

Net return must deduct modeled trading costs:

```text
net_return[t] = gross_return[t] - turnover[t] * cost_rate
```

## Metrics

Report both performance and implementation quality:

### Performance

- cumulative return
- compound annual growth rate
- annualized volatility
- Sharpe ratio
- Sortino ratio
- maximum drawdown
- Calmar ratio
- 95% and 99% historical Value at Risk
- expected shortfall, when implemented

### Portfolio quality

- annual turnover
- average number of holdings
- maximum and average concentration
- weight stability between rebalances
- transaction-cost drag
- percentage of failed or excluded tickers

### Relative performance

- excess return over equal weight
- excess return over market benchmark
- tracking error
- information ratio
- rolling Sharpe ratio
- rolling drawdown

## Sentiment ablation

To determine whether FinBERT adds value, compare:

1. MPT only
2. MPT plus raw FinBERT score
3. MPT plus confidence-weighted sentiment
4. MPT plus recency/source-weighted sentiment
5. equal weight

Keep all other assumptions identical. Report performance by market regime and include uncertainty intervals. A higher in-sample Sharpe ratio alone is not enough evidence.

## Sensitivity analysis

Test the system across:

- multiple lookback windows
- weekly, monthly, and quarterly rebalancing
- different risk-free rates
- alternative concentration caps
- different transaction costs
- multiple sentiment blend values
- covariance shrinkage versus sample covariance
- calm, crisis, rising-rate, and recovery periods

Avoid selecting a single parameter because it performed best on the full evaluation period. Choose parameters using a training/validation process and report untouched test results.

## Minimum acceptance criteria

Before describing the strategy as validated:

- no known look-ahead leakage
- a point-in-time universe or explicit survivorship-bias disclosure
- costs and turnover included
- comparison against simple baselines
- untouched out-of-sample period
- reproducible run metadata
- parameter sensitivity reported
- failures and missing data disclosed
- no claim that historical outperformance guarantees future returns
